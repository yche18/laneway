# Laneway deployment

This package runs the web client, Java service, MySQL, Redis, and Memcached with Docker Compose. Nginx serves the client and proxies `/api` to Java. The deployment uses Java 8 and the versions pinned in `compose.yml` and `Dockerfile`.

Kafka, RocketMQ, and Canal are disabled in this deployment profile. Order processing retains the local outbox/inbox and Redis Stream paths. Direct database changes are not propagated by CDC in this profile; use application APIs for updates. For the full middleware stack, use `dev/docker-compose.yml` from the repository.

## Build and package

From the repository root, with Java 8, Maven, and Python 3 installed:

```sh
mvn -Dmaven.test.skip=true package
python3 deploy/package-release.py
```

Alternatively, build using the Java 8 Maven container:

```sh
docker run --rm -v "$PWD:/workspace" -v laneway_maven-cache:/root/.m2 -w /workspace maven:3.9-eclipse-temurin-8 mvn -Dmaven.test.skip=true package
python3 deploy/package-release.py
```

The result is `target/laneway-cloud-release.tar.gz`. It contains the current JAR, frontend, initial SQL, images, deployment configuration, and a SHA-256 manifest. Credentials and local database contents are excluded. The package command rejects a JAR older than the current sources or configuration. These build commands skip business tests; run the isolated regression suite separately before release.

Place any available initial image files in `data/images`, retaining the relative filenames referenced by the database. The repository does not include the original local image collection. Without those files, the application can start but the corresponding images remain unavailable; the frontend provides an image placeholder. Some seeded images use third-party URLs whose availability is external to this project. The package script does not download or fabricate missing images.

## Install and start

Copy the archive to your server and extract it into a new deployment directory:

```sh
mkdir -p /opt/laneway-cloud
tar -xzf laneway-cloud-release.tar.gz -C /opt/laneway-cloud --strip-components=1
cd /opt/laneway-cloud
sh init-env.sh
docker compose --env-file .env -f compose.yml config --quiet
docker compose --env-file .env -f compose.yml up -d --build
docker compose --env-file .env -f compose.yml ps -a
curl -i http://127.0.0.1:8080/api/shop-type/list
```

`init-env.sh` needs OpenSSL and creates independent random database, Redis, and monitoring credentials. It sets `.env` permissions to 600 and does not overwrite an existing file. MySQL uses the `laneway` database and the `laneway_app` application account. Initial SQL is imported only when MySQL creates its data volume; Flyway applies subsequent migrations at application startup.

Open `http://SERVER:8080/` after allowing the configured web port through the server firewall and network access rules. Configure a domain and HTTPS before sharing credentials over a public connection; this package does not provision TLS certificates. Java binds to server localhost on port 8081. MySQL, Redis, and Memcached do not publish host ports. Public Nginx access excludes operations and Prometheus routes.

The `image-init` service copies missing initial images into the uploads volume and exits successfully. It preserves existing files. Web health checks wait for the Java health endpoint.

## Configuration and feature boundaries

Edit `.env` and recreate the affected service to apply changes:

```sh
docker compose --env-file .env -f compose.yml up -d --no-deps java
```

- `LANEWAY_WEB_PORT`: web port, default 8080.
- `LANEWAY_ADMIN_IDS`: comma-separated authenticated user IDs allowed to manage catalog data. Obtain the actual ID from `/api/user/me` after signing in.
- `LANEWAY_PAYMENT_MOCK_ENABLED`: enables simulated payments when explicitly set to `true`; default `false`.
- Database, Redis, and monitoring credentials are generated by `init-env.sh`.

Login codes are written to application logs; SMS delivery is not integrated. After requesting a code, an operator can retrieve it using `docker compose --env-file .env -f compose.yml logs --since=2m java`. Do not publish application logs or authentication tokens.

Simulated payment does not transfer money. Real payment, refund, and voucher redemption integrations are incomplete. A seckill `SUCCESS` status means the order is persisted, not paid. Unpaid ordinary orders can be cancelled; user cancellation of seckill orders is not supported. Administrators must prepare and publish valid seckill offers before they can be ordered.

The experience page shows current cache traces and available capabilities. Disabled messaging and CDC capabilities are expected in this profile. A historical test report, when present, records its own execution scope and does not prove the current deployment has passed the same checks.

## Operations and upgrades

```sh
docker compose --env-file .env -f compose.yml logs --tail=100 mysql java web
docker stats --no-stream
docker compose --env-file .env -f compose.yml down
docker compose --env-file .env -f compose.yml up -d
```

Stopping with `down` preserves data volumes. Do not use `down -v` when data must be retained. Back up MySQL, Redis persistence, uploads, and `.env` before upgrading. Keep the existing credentials and data volumes when replacing release files, then run `up -d --build`. Initial SQL is not an upgrade script and must not be manually imported over an existing database. Upgrades are in place and can interrupt service.

Container limits are 512 MB each for Java and MySQL, 192 MB for Redis, and 64 MB each for Memcached and Nginx. Java heap is capped at 256 MB. These limits are starting values rather than a capacity guarantee; startup peaks, native memory, other processes, and actual load require measurement. Redis uses `noeviction` and rejects new writes when its memory limit is reached. Logs rotate at three 10 MB files per container.

After installation, check application health, shop queries, available images, login, access controls, ordinary voucher ordering, and cache observations. Verify external access independently of localhost checks. This document describes deployment commands and does not claim a deployment or load test has been performed on your server.
